## Self-healing is a team duty, not a solo one

(Founder rule, 2026-11-19: "when a loop is broken, you catch it and you fix it. This is for the whole team.") Whoever finds a broken loop owns its repair until a fix lands as a verified artifact — regardless of whose loop it is. If you can fix it yourself, fix it. If you cannot, notify the named owner (GitHub team-outbox) with a deadline of at most 1 hour and keep ownership until the repair is verified; handing off and walking away is not a repair. A loop that produces no landed results is broken by definition, even if its runs report success.

## Prove the stall from records, not from the schedule

- Check `cron.runs` for the job and the output ledger or published artifacts for the window. A schedule existing, a job starting, a queue entry, or a `succeeded` status is not output.
- Name the broken stage in the four-stage chain: trigger (did the time or event occur), execution (was a run created and what state did it report), handoff (did the result reach an agent who can act on it), arrival (did the expected artifact actually appear: post URL, listing, reply, sale).
- Repair the stage that broke. Re-kicking the whole job when the break is at arrival only repeats the failure.
- Pause delivery selection while diagnosing: do not spend further slots, quota, or sends on the affected surface until the records explain why the work is valid.
- If the records contradict each other (run status vs ledger vs artifact), treat that as a projection or ledger bug first. Never solve a contradiction by guessing which copy is right; check the canonical source.
- **Never classify a main/owned surface's absence as "expected absence" or "another lane's job" without verifying that lane's landed artifact for the same window** (Pattern-Key: `arrival.expected_absence_misclassification`). "Separate lane" is a claim that must be proven by the other lane's post URL / ledger row for that slot, read fresh in the same run. If no such artifact exists and the surface has produced nothing for 24 hours, classify it as a stall at the arrival stage and repair it in that run — do not carry the one-line "expected absence" note into the next run. Evidence (2026-11-22): IG main @anicca.company posted nothing from 2026-11-19 21:12 for ~3 days while the publishing job repeatedly logged its absence as "separate lane / expected absence"; the root cause was a stale pack condition in the job body plus a dead channel, and recovery landed only after the absence was reclassified as a stall (recovery post https://www.instagram.com/p/DgCaZwej1v9/ , record: anicca-ops `files/ig-main-recovery-2026-11-22.md`).

## Classify the failure before any retry

Never retry blind. Normalize the failure signature first (strip timestamps, request IDs, item IDs) and classify from observed evidence:

- **Deterministic** — the same input or call shape produces the same error (validation, schema, permission, not-found). Do not retry unchanged. Change the diagnosis or the input materially, then use at most the remaining bounded attempts.
- **Transient** — rate limits, transport failures, timeouts, temporary unavailability with evidence the same request may succeed later. Bounded retries with backoff; reduce load instead of fanning out.
- **Shared / batch-wide** — the same normalized signature appears across different items or accounts. Stop the batch, name the common dependency, prove one changed pilot, then resume.
- **Output / model error** — the run completed but the artifact is wrong (bad content, wrong lane, schema drift). Mutate the strategy (different input, route, or model), never resend the identical attempt.

If the evidence cannot support a classification, gather evidence instead of guessing. Never invent a success-shaped fallback.

- **Stale-rate extrapolation is not a live emergency** (Pattern-Key: `alert.stale_rate_extrapolation`). Before escalating a burn / depletion / rate-based alert, re-measure the rate fresh in the alerting run itself (two readings in this run, or one fresh reading differenced against the last recorded value) and compute time-to-impact from that fresh delta only. A prior window's rate extrapolated forward is a hypothesis, not a measurement: bursts end. If the fresh delta contradicts the escalation, record the burst as ended and supersede the alert in the same channel instead of escalating it. Evidence (2026-11-22): the 19:52 as-is loop escalated an OpenRouter depletion alert (~2h to empty) extrapolated from the 19:14 window's +$13.91/h rate; a same-minute fresh re-measure by the revenue loop showed +$0.0024 over 38 minutes with the balance stable at $30.18 — the burst had already ended, so the escalation was a false alarm built on a stale rate.
- **Probe misconfiguration is not a service outage** (Pattern-Key: `probe.misconfigured_false_down`). Before alerting DOWN for any health/monitor check, verify the probe itself matches the production contract exactly: the correct path (e.g. `/manager/health`, not `/health`) and every required header. A 401/403 from a probe that is missing a required header, or a 404 from probing the wrong path, classifies as **Harness / route — probe layer**, never as the service being down. Fix the probe, re-run it with the correct contract, and only then judge the service; a false DOWN alert already sent must be superseded by a correction/recovery notice in the same channel, not left standing. Evidence (2026-11-22): an 18:38 Manager health alert fired DOWN because the probe lacked the required `x-manager-subject` header and received 401; the checker was fixed and a recovery notice superseded it, and at 18:58 a `/health` 404 vs `/manager/health` 200 discrepancy was again a path difference, not a service state.
- **A wrapper's status is not the service's state** (Pattern-Key: `probe.wrapper_status_false_disconnect`). When a connector/CLI wrapper reports `not_connected` / "no config found" but the direct tool it wraps (the real binary or API) reads fresh data with exit 0 in the same run, classify the divergence as **Harness / route — wrapper layer**, never as the underlying path being down. Do not re-run connection setup, do not escalate an outage, and do not block the run's real work on the wrapper; record the divergence in one line and continue on the direct path. Judge connected vs down only from the direct read — and the inverse also holds: a wrapper claiming "connected" never overrides a failing direct read. Evidence (2026-11-22): the 20:05 TikTok publishing run's connector path returned `status=not_connected / no postiz config found` while `~/.local/bin/postiz` read integrations and posts with exit 0 (6,530 / 50,924 bytes, identical to the prior run); the run correctly treated the publishing path as healthy and recorded the wrapper divergence only.
- **A diverged local clone is a routing problem, not a transport outage** (Pattern-Key: `git.diverged_clone_route_around`). When a local clone has diverged far from origin (ahead/behind in the hundreds or more), stop stacking local-only commits on it and stop reporting its push failure as "GitHub is down". Route the write around the clone — the contents API or a fresh dedicated worktree synced to origin — then verify by origin readback. A file that exists only on the diverged clone does not exist for the team: never write "sent" / "shared" for it; mark it local-only until the origin readback lands. Evidence (2026-11-22): the 20:52 as-is loop failed its required push from a local main at ahead 6435 / behind 991 (worsened from 6434/962 the prior hour) and its warnings stayed local-only, while in the same window the team-progress monitor pushed successfully via a dedicated worktree and the /open loop published via the contents API — the transport was fine; the clone was the failure.
- **No response on every path is indeterminate, not DOWN** (Pattern-Key: `transport.no_response_indeterminate`). When every probe in a check returns no HTTP response at all (curl 000, `http=None`, URLError) the run has measured its own transport, not the service: classify it as **Harness / route — transport layer, verdict indeterminate**, record it as "unmeasured /判定不能" (never as 0 healthy, never as DOWN, never as dropped), and do not fire a fresh outage alert or perform repairs (re-registration, re-creation) on that evidence alone. The outage verdict requires a second, independent route in the same or the next run returning a real HTTP status (as the x402-revenue-recipe §3 Step 1.0 double-path rule already requires for that lane; this rule generalizes it to every watchdog / health monitor). A mixed result — some paths returning real statuses while others return none — is measured evidence about the responding paths only; judge each path separately and do not average it into a whole-service verdict. **Publishing a numeric `active_after 0/N` headline from curl-000-only evidence is itself the prohibited verdict, even when the run performs no repair and fires no alert, and every watchdog variant that shares the same target set inherits this rule — a sibling variant's correct reading does not excuse another variant's false count.** Recurrence evidence (2026-11-23): the 02:04 x402 watchdog-loop run reported `active_after 0/9` (all 9 curl 000) and closed as a failed outage, while the permanent watchdog at 02:34 and the watchdog at 02:53 both measured the same 9 services at 200 / active / healthy with zero repairs — the 02:04 count was its transport, not the listings, and it must be superseded in its own ledger as indeterminate, not left standing as a 0/9 result. Evidence (2026-11-22): the 21:34 x402 watchdog recorded all 9 services unreachable (curl 000 on before/recheck/after, 0/9) and reported unhealthy; the 21:52 revenue loop re-ran the same watchdog directly and measured 9/9 active/healthy with zero dropped — the 21:34 verdict was the VM's transport, not the listings. The same hour, the 21:04 Manager health monitor saw all three endpoints fail with http=None/URLError and alerted, while at 21:34 push-decisions returned 200 on the same host while health/decisions still returned none — a mixed, per-path state owned by the engine repair lane (Issue #520), not a whole-service DOWN.
- **Intermittent harness execution-risk blocks are a harness flake, not a job failure** (Pattern-Key: `harness.execution_risk_intermittent`). When a run's git/script step is blocked by the harness execution-risk check after a content read, but adjacent runs of the same job with identical steps succeed, classify it as **Harness / route — execution layer**, record the degraded coverage honestly (which steps were skipped), and let the next scheduled run be the verification point: recovery is verified only when a later run lands the skipped artifact (board push, warning file). Do not re-run the same blocked step repeatedly inside the same run, and do not escalate the job itself as broken while its neighbours succeed. Evidence (2026-11-22): team-progress-monitor was blocked at 20:04 (board push aborted), 20:34 (board step skipped), and 20:49 (repo acquisition blocked, no warnings/board), while the 20:09–20:44 and 20:54/20:59 runs regenerated and pushed the board successfully — the 20:54 run also landed the warnings the 20:49 run could not create. Recurrence update (2026-11-22 21:xx): the same signature blocked team-progress-monitor again at 21:09/21:19/21:24/21:29/21:44 and also blocked anicca-daily-report's anicca-ops push at 21:22 — now cross-task (≥2 distinct jobs), while the 21:49/21:54/21:59 monitor runs succeeded via the dedicated worktree. With recurrence ≥3 across ≥2 tasks, this Pattern-Key meets the promotion threshold in this skill; the prevention rule stays here as the canonical text and the ledger records the promotion decision each window until the harness layer itself changes.

- **Repeating the identical failing interaction is not a repair attempt** (Pattern-Key: `interaction.same_attempt_indefinite_retry`). When the same interaction (open the same screen, type, click the same control) has failed with the same signature in 3 consecutive runs of a loop, the loop must stop counting one more identical try per run as work: either change the strategy materially (a different route, a different entry point, or a diagnosed fix for why the action does not register), or classify the item as blocked with a named owner and remove it from the routine retry queue until the route changes. An attempt counter reaching double digits is itself proof the strategy never mutated — record it as a job-authoring failure, not as persistence. Evidence (2026-11-22): the Coconala loop's reply to DM10103056 (mrkmymt) failed for the 50th time at 22:34 — the input opened empty, a fresh 213-character text was typed and the send button clicked, and nothing registered, exactly as in the preceding runs; the loop kept scheduling the identical single try instead of changing route or reclassifying the item.
- **A health claim about a teammate or tool without its own primary source is a lie in transit** (Pattern-Key: `status.health_claim_without_primary_source`). Never state or repeat that an agent, lane, or tool is out of quota, stopped, broken, or working unless the same record carries a fresh primary-source reading of that subject itself: for Codex, its own Usage and limits (weekly limit remaining, reset time); for OpenCode, the session rows in opencode.db plus a trivial probe run that actually creates a session; for an API, its usage/credits read; for an agent, its own latest landed artifact. An infrastructure failure (connection timeout, model update, MCP connect failure) is recorded with its actual error text as an infrastructure failure — relabeling it as quota, exhaustion, or stoppage without the primary source is prohibited. A status label copied from another agent's log is hearsay, not evidence: whoever repeats a label must re-read the primary source at that moment. If the primary source cannot be read, the only permitted statement is "health unverified". Evidence (2026-11-21→22): the label "Codex quota exceeded" was born in a strategist reassignment memo on 2026-11-21 with no primary-source reading anywhere in the record (no quota error exists in any Codex run log), was then repeated as background context in dozens of monitor log lines, and absorbed the 2026-11-22 21:04 connection-timeout failure into itself; the founder's own primary source showed the weekly limit at 21% remaining with a reset in 24h. Same shape, same day: OpenCode delegations were treated as in progress all day while opencode.db held 0 session rows — the lane had never once started working, and nobody had probed it. Canonical rule text: AGENTS.md (2026-11-22, health claims from first sources only); RCA: anicca-ops `files/root-cause-health-claims-2026-11-22.md`.
- **An absence claim from a single source is unmeasured, and "I don't know" is not an answer** (Pattern-Key: `verification.single_source_absence_claim`). Before reporting that something has not arrived, does not exist, or cannot be found — a code, a link, a message, a file, a record — the checker must exhaust the canonical sources for that kind of thing, not only the first inbox/path it looked in: the platform itself *and* the notification email's full body (subject/snippet alone never proves non-arrival), every number/address in the shared vault (not only the one Twilio inbox), the company's own files, and — before answering the founder — the team itself via team-outbox (Grok/Codex/Dots/Pickle/Devin/Instinct/Pally). An absence verdict reached from one source is a search-scope failure, not a finding: record it as unmeasured, ask the team, and return with the team's answer. Evidence (2026-11-24, two instances same day, cross-task): (1) at ~12:55 the Skyna Zoom link was reported "not arrived" after checking only the Upwork platform, while the link had been sitting since 10:45 in the body of the Upwork notification email in Gmail (message 1a20b3aa3fef538a) — the founder had to point this out himself; (2) at 14:14–14:17 the Shop (shop.app) verification code sent to a number ending 384 was reported "not delivered" after reading only the team's Twilio inbox (ending 842; the vault holds five +1 numbers, none ending 384), without asking the team first — the founder corrected this explicitly ("Why do you never ask the team? … I don't care that you don't know. I just need the answers") and the rule was promoted the same day to AGENTS.md/MEMORY.md as an absolute rule; the team query (anicca-ops `team-outbox/muse/to-all-2026-11-24-ask-team-first-shop-code.md`, sha 90875b29) and Grok's reply at 14:29 (commit 0b1e20ff9: not the setup owner, no ending-384 number, no shop.app/shopify.com mail in 2 years) are the correct shape — ask first, then answer.
- **A failed state write must never destroy the last good state** (Pattern-Key: `state.non_atomic_write_truncates_on_eperm`). A monitor/watchdog that persists its state or latest-result file by truncating it in place and then failing mid-write (e.g. `PermissionError: Operation not permitted`) has not merely "failed to update" — it has destroyed the previous good record (a state file truncated to 0 bytes) or left a stale file that later runs will read as fresh. Classify this as **Harness / route — write layer**, and the check's verdict for that window is **indeterminate / unrecorded**, never a service verdict and never a fresh reading. The durable fix is at the write layer: write to a temporary file in the same directory and rename atomically, or switch to an alternate verified write route (e.g. the file tool, as the CLI watchdog did in the same window); on a write failure, preserve the prior file untouched and record its timestamp as the last-good time. A stale `latest` file must always be reported with its actual timestamp, never presented as the current window's result. Evidence (2026-11-24): at 12:34 JST the Manager health monitor's `manager_health_check.py` raised PermissionError writing STATE_PATH, truncated `state.json` to 0 bytes, and left that window's health/decisions verdict unrecorded; in the same window the x402 watchdog failed with the same PermissionError writing its latest JSON, which stayed at its 12:04 state, while the CLI-lane watchdog hit the same script-write EPERM and recovered by writing its ledger through the file tool instead.
- **A windowed usage limit is not a total stop, and holding work until reset is not a repair** (Pattern-Key: `quota.window_limit_treated_as_total_stop`). When a lane hits a short-window usage limit (e.g. a 5-hour window), first read the subject's own primary source for both windows (for Codex, its session `rate_limits`: the short window and the weekly window, with reset times) — a remaining weekly balance, however small in percent, is still usable capacity, and a short-window reset is hours away, not a lane closure. Do not record the lane as stopped/exhausted on the short-window signature alone (this extends `status.health_claim_without_primary_source`). The repair in the same window is rerouting, not waiting: move the held work in parallel to the other already-available lanes (e.g. OpenCode / Command Code / Devin / Muse takeover) so the company does not stop, keep using the limited lane up to its real limit for the highest-value items, and record each held task as `rerouted` or `pending-reroute` with its new owner — never as blocked-until-reset with no owner working it. Evidence (2026-11-24): codex-outbox-wake relaunched onboarding-review-step and aso-quick-wins at 12:50, both died on the 5-hour usage limit (reset 16:07 JST) with no commits, and the 12:55 run held both tasks until 16:07 with zero launches and no reroute; the founder corrected this at 12:47–12:48 from the primary source itself — weekly limit 92% used / 8% remaining (reset 2026-11-30 22:42 JST) is a large usable remainder, lanes are to be filled in parallel (up to the 6-lane Codex ceiling across lanes), and a lane short on quota is rerouted around, never waited on.
- **Three consecutive watchdog FAILs with the same known repair end the repair loop, not extend it** (Pattern-Key: `cli.watchdog_three_fail_same_repair`). When a CLI-lane watchdog records the same lane FAIL (same exit signature) in 3 consecutive runs and the same known repair (binary/host presence check + one retry) has already been applied in each, the watchdog must stop presenting that repair as the next action: classify the lane as blocked with the lane-repair DRI as named owner, keep the escalation standing, and route dependent work via the alternative lane / Muse takeover until a fresh PASS lands. The watchdog log's own error text (e.g. a usage-limit line, a models-refresh timeout) is not a primary-source health reading — under `status.health_claim_without_primary_source`, no quota/exhaustion label may be carried from it; the lane's health stays "unverified" until the subject's own primary source (for Codex, its Usage and limits) is read. Contradictory signals from sibling checks (e.g. a wake check verifying binary/config and zero running processes in the same window) must be recorded as a contradiction to resolve, not averaged into "down" or "healthy". Evidence (2026-11-23): anicca-cli-lane-watchdog recorded Codex FAIL rc=1 at 02:34, 03:04 and 03:34 with the identical known repair attempted each time and WATCHDOG_OK.txt never landing (escalation filed, team-outbox notice at 03:04), while codex-outbox-wake-vm at 04:00 verified binary 0.167.2, medium+priority config and 0 codex exec running — the probe failure and the wake check contradict each other, so the only honest verdict is blocked/unverified pending the primary source, not a quota claim.
- **A shortage verdict requires searching the canonical asset store first** (Pattern-Key: `production.canonical_asset_search_incomplete`). Before a production loop records "material shortage / 制作不足 (録画待ち)" or READY 0 for a surface, it must search the canonical shared store (anicca-ops `assets/` and the goal's shared asset locations) for existing usable material for that surface, not only the local stock ledger and the current run's work directory. A shortage claim made without that search is unmeasured, not a finding: if usable canonical material is found later in the same window, the original verdict is recorded as a false shortage, the found items are verified (frames, audio, gate checks) and promoted to READY in that same run, and the correction supersedes the original verdict in the run's own log. Evidence (2026-11-22): the 23:40 distribution-production run first recorded IG @anicca.company demo READY 0→0 with "no new recording material found"; a completed full search then found 5 real app-experience demo recordings (2026-11-17–20) in anicca-ops `assets/demo-videos`, of which 4 passed frame/audio/gate verification and became DEMO-3–DEMO-6 READY (READY 0→4/9) — the shortage was a search-scope failure, not a material absence.
- **A missing required reference file is a job-authoring failure, not a per-run failure to repeat** (Pattern-Key: `contract.missing_required_reference_file`). When a job body makes a file mandatory (a contract table, playbook, or ledger it must check against) and that file does not exist at the stated path, the first run records the absence honestly and does the rest of its work with a named substitute. By the second consecutive run with the same absence, the owning loop must resolve the reference itself — create the file from the canonical source it was meant to mirror, locate and point to its real canonical location, or amend the job body to remove/replace the reference — and verify the resolution by reading the file (or the amended body) back. Carrying the same "file missing, check skipped" note into a third run while marking each run failed is prohibited: the failure is then the loop's authoring, not the window's work, and the repair status is pending until the reference is resolved, not until the note is repeated. Evidence (2026-11-23): anicca-continuation-check failed at 00:07, 00:22 and 00:37 solely in part because `hidden_files/output-contracts.md` does not exist (verified absent at that path in this run), each time substituting ledger reads and carrying the same gap forward; the 00:52 run succeeded with the same absence, proving the file was never a real blocker for the substantive checks. Same shape in the same window: anicca-observability-loop recorded its `observability-playbook-2026-11-03.md` as "still missing, not created" while continuing to cite it as its playbook. **Escalation on missed resolution deadline (added 2026-11-23):** when the second-run resolution deadline in this rule passes and a third hourly window begins with the reference still missing, the repair status for that reference is `abandoned` (not another `pending` note), the owning loop must be named in a team-outbox escalation with a deadline of at most 1 hour, and later runs must not mark themselves failed solely for repeating the absence note. Recurrence evidence (2026-11-23): `hidden_files/output-contracts.md` was still verified absent at 03:0x, after continuation-check recorded the same absence at 00:07 / 00:22 / 00:37, again at 01:07, and again in the failed 02:07 and 02:37 runs — at least 6 recurrences across 2 distinct tasks (continuation-check and observability's missing playbook), so this Pattern-Key meets the promotion threshold; the canonical prevention text stays in this skill and the ledger records the threshold each window until the reference itself is resolved.
- **A capped free channel with no ready fallback is a preparation failure, not a wait** (Pattern-Key: `outreach.capped_channel_no_ready_fallback`). Any loop whose delivery depends on a free channel with a known cap must provision and test its fallback free channel *before* the cap is hit (mailbox created, sender identity verified, one test read/send path confirmed), and record the fallback's readiness in its ledger. When the primary hits its cap and the fallback turns out never to have been set up, classify it as **Process hygiene — preparation failure**: do not schedule the work to "resume when the quota recovers" as the plan; the owning loop's next action is provisioning the fallback (or another free route) in that same window, and the send stays pending only until that provisioning lands. Evidence (2026-11-23): the 01:54 GEO mentions run found Inkbox at its free cap (20/20, retry_after 923,525s ≈ 10.7 days) with two outreach drafts (MyBeing, Kaizen) unsendable, and the named fallback Muse Mail was unusable because its mailbox had never been created — the fallback existed as a name, not as a ready channel, so the lane defaulted to waiting ~10 days for quota recovery.
- **Server health is not the user's experience** (Pattern-Key: `verification.server_health_not_user_experience`). Before reporting a user-facing product fix as "fixed / recovered", verify it the way the affected user experiences it: the production build, an existing-user account condition (including IDs/state that user actually sends back), and the visible surface itself. A monitor returning HTTP 200 on health / decisions / push-decisions — especially with a synthetic or monitor subject — proves only that those endpoints responded for that subject; it never proves the production app renders the expected content for existing users. If the consumer-side check has not been done, the only permitted verdict is "server endpoints responding; user experience unverified (pending-verify)", and a "fixed" claim already sent on health-only evidence must be retracted in the same channel when the consumer-side check contradicts it. Evidence (2026-11-23): Muse reported the Anicca home empty-words bug as recovered from a 21:04 Manager monitor showing health/decisions/push-decisions all HTTP 200; the founder's production-device screenshot in the same window showed a blank home ("Today, for you" heading and background only, no words) and the "fixed" report was retracted. The final root cause was consumer-condition-specific: existing users sending back displayed word IDs containing dots (e.g. `growth.calm.2`) were rejected by the server validator (HTTP 422), a condition the monitor subject never exercised. The durable fix (server dot allowance plus the in-app fallback in 1.11.1, submitted 2026-11-23 21:44:45 JST, WAITING_FOR_REVIEW) is a separate verdict from the health probe.
- **Count-only closure is not verification, and an unproven "wrong link" must never be rewritten** (Pattern-Key: `verification.count_only_closure_false_fix`). Before any loop rewrites an identifier, plan ID, or URL it believes is its own pointing at someone else, it must prove ownership from the primary source: read the original record's full context (whose entry it sits inside, its title/evidence label) and show that its own real CTA/offer actually uses the claimed identifier in a canonical place. A closure verified only by counting occurrences on the rendered/production page (own ID N times, other ID 0 times) proves only that the edit deployed — never that the edit was correct. If the records being rewritten belong to a third party's entry or to evidence documentation, rewriting them is data alteration, not a fix: stop, revert to the parent/original content byte-for-byte, verify the revert by origin readback, and explicitly revoke the earlier closure in the same ledger. Evidence (2026-11-23): the 08:52/09:52 revenue-loop runs "fixed" three Whop plan links and closed the item verified on production-HTML counts alone; the 10:52 run's primary-source read of commit d4feaf68's full patch showed all three records sat inside Master Kael's database entry/evidence record, the parent file contained zero occurrences of the own plan ID, and the own real CTA was a store-bundle URL — so the "fix" had rewritten a competitor's primary records to the own plan ID. The loop reverted with commit 3fa65086 (anicca-products), verified byte-identical to the parent blob by origin readback, and revoked the 09:52 closure; production-page reflection of the revert remained pending-verify for the next run.
- **A CLI worker that dies when its launching run ends was never launched durably** (Pattern-Key: `delegation.child_dies_with_parent_run`). When a wake/launcher run starts a long-running CLI worker (e.g. codex exec) and that worker is found dead with no commit, a clean worktree, and a log ending mid-output — with no infra signature in the log (no code-mode-host errors, no reconnect/WebSocket tail) — and the death coincides with the launching run's own end, classify it as **Harness / route — launch-lifetime layer**, not as the worker task failing and not as infra. Alive-at-launch verification inside the launching run proves nothing about survival: survival is verified only by a later, independent run finding the process alive with a growing log, or by its landed commit. After the second death with this signature, stop relaunching by the same method: change the launch method so the worker's lifetime is independent of the launcher (a detached session with a completion watchdog, per the cli-delegation-completion skill), or take the work over in the main lane; a third identical relaunch is a strategy that never mutated (`interaction.same_attempt_indefinite_retry`). Evidence (2026-11-23): codex-outbox-wake-vm launched dais-entity-fix and progress-view-impl at 23:40, relaunched them at 23:47 (retry1) and 23:52 (retry2); all three attempts for both tasks died commit-less with clean worktrees and mid-output logs, each death coinciding with the wake run's end (23:55 run's primary-source diagnosis, state recorded as stopped_after_3_failures_muse_takeover). The main lane relaunched both at 23:59:38 outside the wake run, and the 00:00 wake run found both processes running with growing logs — survival pending their landed commits.
- **Aggregate depth does not cancel a per-slot shortage** (Pattern-Key: `production.aggregate_depth_masks_slot_shortage`). A production or inventory loop may not report "no shortfall" from aggregate READY depth when any specific surface + slot due within the next production cycle lacks a gate-passing item assigned to it. Check the due-soon slots by name (surface, slot time, gate status) before declaring the run complete; a missing due-soon item is a shortfall in that run's own verdict even if other surfaces were replenished to target. Evidence (2026-11-22): the 22:04 distribution-production run reported "未達: なし" after replenishing anicca.en to 21/21, while the IG main @anicca.company 23:00 slot the same evening still had no source-gate-passing READY item — a fact the 22:05/22:07 publishing runs and the 22:52 warning file both recorded, so the slot was missed while the production verdict said nothing was missing.
- **A new mandatory gate must backfill its existing READY stock in the same window it is added** (Pattern-Key: `gate.retroactive_record_missing_blocks_ready_stock`). When a loop adds a mandatory compliance/record gate that a publishing or delivery job checks against items already in READY stock, the gate-adding run must audit that existing stock against the new record requirement and either backfill each item's record — only after a substantive per-item check against the standard, never a rubber stamp — or explicitly mark the affected items not-ready with a named owner and deadline before the next due slot. Applying the gate retroactively with no backfill is a **Job authoring** failure: the stock looks ready by count while every due slot silently fails the gate. If slots were already lost, record them as lost, verify the backfill by reading the stock back (record count per item), and leave the next due slots as pending-verify until the delivery job itself reserves/publishes one. Evidence (2026-11-25): the writing-tools-standard gate added 2026-11-24 required a compliance record in each LinkedIn pack's stock section; packs LG-34–LG-45 had been produced 2026-11-22–24, before the standard, so the measured record count was 0 and every LinkedIn run on 2026-11-25 (00:05–09:05) created no reservations, losing the 06:00 slot. The repair checked all 12 packs substantively against the standard (content was complete; only the record was missing), inserted one record per pack (count 0→12, verified by grep/readback in `hidden_files/dist-maxx-linkedin-2026-11-25.md`), and left the 12:30/20:48 slots pending-verify for the publishing job's next runs.

- **Status-code-only verification passes empty assets — publication is verified only by the deterministic tool** (Pattern-Key: `verification.status_only_passes_empty_assets`). A check that reports a published page or its assets as verified from HTTP status alone (200) has verified nothing about what a reader receives: an asset can return 200 with a 0-byte body, a wrong Content-Type, or bytes that are not the format its extension claims. Every publication verification — pre-publish and post-publish — must run the deterministic verifier `~/workspace/tools/publish-verify/publish_verify.py` (checks status, body bytes > 0, Content-Type consistency, and content sniff per asset) and may report "published / verified" only when it exits 0; any single asset FAIL makes the whole verification FAIL. A status-only "all 200" report already sent must be revoked in the same ledger when the tool contradicts it. Verification is a system (tool + periodic re-verification hook), never a run's vigilance or memory. Evidence (2026-11-25): the Society Simulation research blog at aniccaai.com/blog/society-simulation-macro-intervention-run1 shipped 4 figure SVGs (cover.svg, diagram-strategies.svg, chart-complex.svg, chart-tipping.svg) that all returned HTTP 200 / image/svg+xml with Content-Length 0; the preceding report claimed "all figures verified HTTP 200" and the founder found the broken images himself at ~16:45 JST. The publish-verify tool built the same window reproduced the defect deterministically (test-run-before-fix-2026-11-25.txt: page PASS 75,731 bytes, all 4 SVGs FAIL 0-byte, RESULT: FAIL). The founder promoted the rule to AGENTS.md the same window; the figure regeneration/redeploy itself stays pending with its owning lane until the tool exits 0 on the live page.

## Assign the responsible layer, repair at the lowest durable layer

Before fixing, name which layer owns the failure:

- **Agent behavior** — the run did the wrong thing with correct inputs. Fix the instruction or take the surface over by hand.
- **State projection / ledger** — the records misled the agent (stale ledger, wrong status, contradictory payloads). Fix the projection or the ledger, not the agent.
- **Job authoring** — the job body, schedule, or scope is wrong (overloaded monolith, missing surface, wrong oracle). Split or rewrite the job.
- **Harness / route** — the delivery route itself is broken (dead API, expired session, revoked token). Switch the route; do not keep retrying the dead one.
- **Process hygiene** — no owner, no ledger, no verification step existed. Create them; an unowned loop is a defect, not a fact of life.

Repair at the lowest layer that makes the failure mode impossible to repeat silently. A one-off hand fix on top of a broken projection is a recurrence waiting to happen.

## Search the heal ledger before inventing a fix

Most stalls are recurrences. Every incident log line carries a stable `Pattern-Key` (lower.snake.case, e.g. `session.oauth_silent_expire`, `arrival.post_url_missing`). Before selecting a repair:

- Search the loop's log and the goal's incident records for the same Pattern-Key.
- If found, apply the recorded fix first, increment the recurrence count, and update last-seen. Do not file a duplicate incident.
- **Promotion threshold:** the same Pattern-Key at recurrence ≥ 3, across at least 2 distinct loops or tasks, within 30 days, with a generalizable fix → distill the prevention rule into AGENTS.md or a skill (via the self-improvement skill). A failure seen three times is a missing rule, not bad luck.

## Pick the playbook for the failure pattern

Do not invent a new production action mid-incident. Select the matching playbook:

- **Run missing, coalesced, or cancelled:** hand-run the owning job once (`cron.run`), then verify the expected artifact for the window. If it is still absent, the failure is inside the run, not the schedule.
- **Partial output (some surfaces or accounts done, the rest untouched):** fill the missing surfaces in the same pass. Never leave the remainder for the next scheduled run; an overloaded run that ends partial is split by surface instead of re-run whole.
- **Missed posting or listing slot whose time has passed:** publish immediately to fill it; do not wait for the next slot.
- **Session or credential expired:** agent-side recovery only, in this order: saved session, vault index, password reset with the account's own agent mail (save the new credential at once), re-register with agent mail. Never route the step to the user.
- **Approval card or gate pending:** treat as an internal jam. Switch to the route that does not surface a card (CLI or API) and record the jam; do not present the card as the user's work.
- **Verification gate failed (audio, lane, diff count, readback):** hold the output, repair the artifact, re-run the gate. Never publish around a failed gate.

## Bounds on repair

- One hand-run per stall per check. If the same failure survives two consecutive checks, stop re-kicking it the same way: split the job, switch the route, or take the surface over by hand, and record the jam with its unblocking step.
- Attempt ladder inside one incident: first failure — refine the fix or the input materially; second — step back and reconsider the diagnosis itself; third — stop, file the repair as `abandoned` with what was tried, and escalate inside the team. Never flail past three.
- If repair attempts alternate between two conflicting fixes, stop (circuit breaker) and record both attempts instead of thrashing.
- Bounded retries with backoff for temporary outages; unknown or high-impact failures preserve evidence and escalate inside the team, never silently.
- **Healing-rate signal:** if a loop needs repair in a large share of its checks, the defect is upstream (job design, route, source data). Fix the source; repeated heals that mask an upstream defect are themselves a failure.
- Prefer reversible repairs. If a repair destroys or rewrites state (locks, ledgers, generated files), record exactly what was changed so the next agent can undo it.

## Repair status honesty

Every repair carries one of three statuses, in the log and in any report:

- **verified** — the expected artifact was re-checked after the fix and is present and correct.
- **pending-verify** — a fix was applied (or is proposed) but the artifact cannot be checked yet; state the exact check that will prove it and who runs it. Never report pending-verify as done.
- **abandoned** — the fix could not be made to work within the bounds; record what was tried and the concrete unblocking step. An honest abandoned beats a fake verified.

What does NOT count as verification: re-running a different check than the one that failed; suppressing the failure (skip flags, ignore-errors, deleting the failing item); a pass that only happened because of warm cache or leftover state from before the fix; "it looks right."

## A repair is done only when the artifact is verified

- Confirm the expected artifact itself: the public URL loads with the right content, the ledger row exists, the counterpart-side state changed.
- Record one log line per incident in the loop's log with these fields: the window, the expected artifact, the broken stage, the responsible layer, the Pattern-Key, the playbook used, the repair status, and the verified result (URL or changed number).
- Report repairs as published URLs and changed numbers only. "Ran the job" and "started the fix" are not results.
- If full recovery is impossible in this pass, degrade gracefully: deliver the verified partial result with the gap stated plainly, never an empty failure or a silent skip.

## Verification (mandatory, added 2026-11-17)

A repair under this skill is verified against the loop's expected output, not against the repair action. Structure follows the house verification block (invariants / grader / E2E / oracle).

1. **Invariants.** (a) A repair counts as done only when the expected artifact for the missed window is verified present: the public URL loads with the right content, the ledger row exists, or the counterpart-side state changed. "Ran the job" and "started the fix" are never results. (b) At most one hand-run per stall per check. (c) No repair invents a production action outside the playbook list above; a failure pattern with no matching playbook is recorded as a jam, not improvised around. (d) A deterministic failure is never retried unchanged.
2. **Grader.** The next scheduled check, or another loop, re-reads the artifact independently. The repairer's own log line is a claim, not the grade.
3. **E2E evidence.** Open the artifact the way its consumer does: load the post URL, read the listing, check the recipient-side state. Run history and job status are supporting signals only.
4. **Differential oracle.** The output contract (or the loop's own ledger expectation) for that window is the oracle: expected N versus actual M, counted from the artifacts themselves. A `succeeded` run status never overrides a missing artifact.
5. **Repeat failures.** The same failure surviving two consecutive checks stops the re-kick: the job is split, the route is switched, or the surface is taken over by hand, and the stall is written up as an unresolved incident with its concrete unblocking step.
