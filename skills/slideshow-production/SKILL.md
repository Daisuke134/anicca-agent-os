# スライドショー制作（勝者コピー型）

伸びた投稿の形式を、実測の数字で確定し、実物をそのままコピーして作る手順。
オリジナルの形式は作らない。勝者の運用全体（形式・量・頻度・検証）をコピーする。

このスキルは2026-11-15に実証された手順の初版である。実測の合格値と失敗例は全て同日の実物に基づく。

## 原則

1. **勝者は数字で決める。** 印象やフォロワー数ではなく、その投稿の再生数を実測して一番伸びたものを勝者にする。
2. **作る前に実物を見る。** 対象アカウントのプロフィールと勝者投稿そのものを自分の目で開いてから、言語・形式・レイアウトを決める。推測で決めない。
3. **変えるのはフックと文面だけ。** 背景写真セット、レイアウト、文字の置き方、書体は勝者の実物のまま使う。
4. **出す前に検証する。** 全スライドを勝者と並べて目視し、ピクセル比較で数字にする。検証していないものは出さない。
5. **全投稿に出典ペア。** 「自社投稿 ← コピー元の勝者投稿（勝者の実測数字）」を台帳に必ず残す。

## Step 0: 対象アカウントの実物確認（最初に必ずやる）

制作に入る前に、対象アカウントのプロフィールを実際に開き、次を確認する。

- 表示名と bio の文面
- **投稿の言語**（日本語か英語か。アカウント名からの推測は禁止）
- 直近投稿の形式（何枚組か、写真か動画か、文字の置き方）

### 失敗例（2026-11-15、@honne_reveal）
@honne_reveal を「日本語アカウント」と誤認し、日本語パック8本を予約まで進めた。後からプロフィールを実物確認したら英語アカウント（表示名「honne」、bio は英語、直近5投稿は全て英語）で、全件の作り直しになった。
**教訓: 言語と形式はプロフィールの実物で決める。予約の前に確認する。**

## Step 1: 勝者選定（実測で確定し、実物を保存する）

1. 候補アカウントの投稿指標を tikwm で実測する。
   - 道具: `~/workspace/tools/tikwm/tikwm <投稿URL>`（公開 API、認証不要・無料。再生・いいね・コメント・共有・保存が全部取れる。写真投稿の再生数も取れる）
2. 再生数の実測が最大の投稿を勝者に固定する。面ごとに勝者は1つ。プラットフォームをまたいだ横展開はしない（その面の勝者をその面でコピーする）。
3. 勝者の実物をダウンロードし、3点セットで保存する。
   - 投稿リンク
   - 実測数字（再生・いいね・保存、計測日時）
   - 全スライドの画像ファイル
   - 保存先の実例: anicca-ops リポ `files/winner-images-2026-11-15/`（命名: `<アカウント>_<投稿ID>_slideNN.jpg`、表紙は `_cover`）
4. 形式が「自社がそのまま再現できる形式」であることを目視で確認する。特定の人間の顔出しトークなど、キャラクター性に依存する形式は数字が大きくても勝者にしない。

## Step 1.5: フック生成（1枚目）— 2026-11-24 追加（本人の直接指示）

**フックは形式の一部ではなく、独立した生成工程である。** この節を通さずに作ったフックは出さない。

### 根本原因の記録（2026-11-24、本人が実物スクショで指摘し確定）

形式凍結（2026-11-17）はフックの形を「〜の口癖5選」とだけ定義し、制作側はその「〜」に痛みの日ラベルを機械的に埋め続けた（「週末に心が重い日の口癖5選」72再生／「未来が不安で動けない日の口癖5選」74再生／「仕事のミスを引きずる日の口癖5選」80再生／「夜に考えすぎてしまう日の口癖5選」24再生）。本スキルにはフックの良し悪しを決める節が存在せず、制作ジョブは本スキルを名指しで参照していなかった。本節がその穴の恒久対策である。

### 勝者フックの型（実測で確定、2026-11-24 tikwm 再実測を含む）

勝ちフックの実例:
- 「メンタルが強い人の口癖５選」@anicca.jp — 再生75,495・いいね1,493・保存199
- 「メンタルが勝手に安定する口癖５選」@anicca.jp — 再生15.4K（ピン留め）／同型 @anicca.jp4 版 再生24,802・保存239
- 「メンタルが安定する口癖、知ってる？」@anicca.jp1 — 再生19,804・いいね3,216（率16.2%）・保存442
- "5 affirmations to tell yourself every morning" @aniccaaffirmation — 再生253,737・保存355
- 「大好き確定セリフ5選」@honnevideo — 再生10,844・保存31

共通構造（5点、全て満たすこと）:
1. **主語は「なりたい姿・肯定的アイデンティティ」か「得られる結果」。** 「メンタルが強い人」「勝手に安定する」。痛みの状態（〜な日・〜で動けない）はタイトルの主語にしない。痛みは2枚目以降のフレーズ側で扱うもので、入口には置かない。
2. **得が1行で即分かる。** 読んだ瞬間に「これを読むと何が得られるか」が分かる（安定する／強い人の真似ができる／毎朝の自分への言葉）。
3. **数字で具体化する。** 「5選」等で全体量と「全部読める」見通しを与える。
4. **工夫語を1つ入れる。** 実測で効いた型: 「勝手に」（努力不要の結果）、「知ってる？」（好奇心ギャップ・疑問形）、「確定」（結果の保証感）。どれか1つでよい。盛らない。
5. **フック単体で独立して働く。** タイトル・キャプションを見ていない前提で、その1行だけで続きを読みたいと思えるか（外部の勝者スキル dontbesilent2025/dbskill `dbs-title-cover-intro` の原則「良い冒頭＝話題＋Hook＋信頼性、冒頭は独立して働く」の採用）。

### 禁止パターン（出したら不合格）

- 「〜な日の口癖5選」型: 痛みの日ラベル（心が重い日／不安で動けない日／ミスを引きずる日／考えすぎる日 等）をタイトル主語にするもの。実測24〜80再生の敗因そのもの。
- なりたい姿も結果も書かれていない、状態の説明だけのタイトル。
- 同じアカウントで同型フックの量産（差別化のない「〜5選」の連番）。フックは毎回、勝者型の範囲で変える（既存ルール「フックは毎回変える」の具体化）。

### 生成手順（制作バッチごとに必須）

1. **勝者フック参照**: バッチの固定勝者（＋自社勝者）のフック実例を最低3本、実物で開いてから書き始める。参照したフックと実測数字を制作記録に残す。
2. **候補を複数出す**: 題材ごとに候補を3本以上出し、上記5点で自己採点する。
3. **バッチ内ランキングで選ぶ**: 候補同士の相対順位で採用を決める（外部の勝者スキル mbfinotti/advertising-skills `ad-hook-analyzer`、MIT・26.6K installs の方式: 絶対スコアでなくバッチ内ランキング＋約束と中身の一致ゲート）。「1行だけ見て続きを読みたいか」を最終ゲートにする。
4. **題材の選び直し**: 題材自体が痛みの日ラベルしか立たない場合は、フックでなく題材を捨てる。勝者型に変換できない題材は作らない。

### 併用スキル（フック工程の正本指定、2026-11-24）

- 生成の考え方: dontbesilent2025/dbskill `dbs-title-cover-intro`（旧 `dbs-hook` 27.3K installs の後継。中国語圏向けのため原則のみ採用し、文面は当社の勝者実例で作る）
- 採点・選定: mbfinotti/advertising-skills `ad-hook-analyzer`（バッチ内ランキング方式）
- 勝者フックの抽出: ScrapeCreators `outlier-post-finder` / `transcript-intelligence`（勝者の outlier 投稿と台詞からフックを抜く。無料枠の範囲）
- 補助: blitz-copy（Hook→Spike→Payoff、ただし数字の捏造禁止の当社ローカルルール優先）、hooked-ux は製品ループ用でありフック生成には使わない、copywriting はページコピー用であり使わない。

## Step 2: 制作（勝者の実物から作る）

1. 勝者スライドの背景をそのまま使う。焼き込まれた文字は inpaint で除去してクリーン背景を作る（型は `assets/scripts/rebuild.py` の `clean()`）。
2. レイアウト・書体・文字の置き方は勝者と同型にする。変えるのはフックと文面だけ。
   - **EN 面の書体仕様（2026-11-15 実測で確定）**: フォントは **TikTok Sans Bold**（`~/workspace/tools/fonts/TikTokSans.ttf`、variable font を `set_variation_by_name('Bold')` で使う）。縁取りは **stroke_width = round(フォントサイズ × 0.075)**（影レイヤーも同幅）。根拠は勝者 @aniccaaffirmation photo/7624115204804267272 のグリフ実測: 数字「5」（fill 高57px）で stem 8px・stroke 6px・グリフ幅75px。TikTok Sans Bold の実測は stem 9px・stroke 6px・幅75px で一致する。
   - **失敗例（2026-11-15、本人指摘「少し太い感じがする」）**: 旧ビルダーは Fredoka（可変フォント weight 600）＋ stroke 固定8px を使っていた。同じ「5」で stem 11px・stroke 8px・幅81px となり、丸みのある字形と合わせて勝者より明らかに太く見えた。**EN 面で Fredoka は使わない**（丸ゴシック系は勝者の字形と違う）。フォントを変えたら、必ず勝者のグリフ寸法（stem／stroke／幅）を同寸法で実測してから使う。
3. **文字は自動縮小（テキストフィット）必須。** 文面の長さに合わせてフォントサイズを自動で縮め、画面内に収める（型は `assets/scripts/build_hr3.py`）。
   - 欠陥の実例: HV2-1 slide03「もっとあなたのこと知りたい」が両端切れのまま QUEUE に入った。端切れは欠陥として作り直す（修正の型は `assets/scripts/build_hv2fix.py`）。
4. **言語混在禁止。** 画像内テキスト・キャプション・ハッシュタグまで、アカウントの言語で統一する。
5. 同じ文面を同じアカウントで繰り返さない。フックは毎回変える。
6. 禁止形式（どの勝者もやっていない形式は出さない）: 無地グラデーション＋一文、白背景＋黒文字の単語カード、紫星空＋丸ゴシック＋一文（いずれも実測で再生24〜105・反応ほぼ0）。

## Step 3: 検証（目視＋ピクセル比較の両方）

1. **全スライド目視**: 自社版と勝者を並べ、全スライド・全フレームを自分の目で見る。文字が入り切っているか（「…」や端切れが無いか）、1画面で全体が見えるか、書体・色が1つのデザインにそろっているかを見る。
2. **pixelmatch で数字にする**: `~/workspace/tools/pixeldiff/`（prep.py で両画像を 540x960 の PNG にそろえ、`node diff.js a.png b.png ラベル` で相違率を出す）。
   - 合格の実測（2026-11-15、作り直し後）: 英語面 8.7〜12.3%／日本語面 1.8〜3.0%／Honne 2.7〜4.8%。差分は変更した文面分のみ。
   - 不合格の実測: 作り直し前は 71.7〜85.5% で別物だった。
3. **注意: pixelmatch は文字切れを検出できない**（背景が支配的だと数字が低く出る）。数字が合格でも目視で端切れがあれば不合格。目視が必須で、数字は補助。
4. **要素単位の照合表（2026-11-24 追加・必須）**: 予約・公開の前に、勝者実物と自社版を要素ごとに照合し制作記録に残す: 被写体（人物の有無・種類）／寸法／枚数／文字サイズと位置／番号の有無／フッターの有無／キャプション形式／音楽。1要素でも不一致なら不合格。文面の転記確認だけでは形式確認にならない（TA2系39本の逸脱は文面確認では検出できなかった）。
5. 検証結果（相違率と目視の判定）は制作記録と台帳に残す。

## Step 4: 公開（Postiz 予約へバルク登録）

1. 投稿は Postiz の予約（QUEUE）へ事前にバルク登録する（枠時刻に手で出さない）。
2. 冪等キーは「連携＋日付＋枠時刻」。登録後に posts:list を再読し、件数・枠時刻・重複なし・error null を実測で確認する。
3. 台帳（posts-ledger）に全投稿を出典ペアで記録する: 自社投稿の Postiz ID と枠時刻 ← 勝者投稿 URL（実測数字）。
4. 在庫ファイルに制作パックを登録し、予約済みは RESERVED、公開済みは USED に更新する。

## Step 5: 計測と倍賭け

1. 投稿後の指標は日次で tikwm により台帳化する（再生・いいね・保存）。
2. 自社投稿が勝者になったら、その自社勝者を倍賭けする: 同じ背景セットと形式のまま、主題とフックだけ変えて出し続ける。その場合も出典は「自社勝者 ← その勝者がコピーした勝者」まで遡って記録する。
3. 伸びない形式は数字で判定して止め、勝者の形式に戻す。

## 検証（必須・2026-11-17 追加）

このスキルで作ったパックは、以下の検証を通って初めて「公開可能」と言える。型は自社の検証ブロック（不変条件／grader／E2E／oracle）に従う。

1. **不変条件**: (a0) **フックは Step 1.5 を通っている**: 参照した勝者フック実例（最低3本・実測数字つき）が制作記録にあり、禁止パターン（痛みの日ラベルを主語にする等）に該当せず、5点構造（なりたい姿／結果が主語・得が1行で分かる・数字・工夫語・単体で働く）を満たす。Step 1.5 を通していないフックは、形式が凍結仕様に一致していても不合格。(a) 勝者は実測の再生数で固定され、投稿リンク・実測数字（再生・いいね・保存、計測日時）・全スライドの実物が保存されている。実測できなかった数字は「未計測」と書く。(b) 変えたのはフックと文面だけであり、背景・レイアウト・文字の置き方は勝者の実物のまま。書体の一致は印象ではなくグリフ寸法（stem／stroke／幅）の実測で判定する（EN 面で Fredoka を使わないのはこの不変条件の実例）。(b2) Step 3 の要素単位照合表（被写体・寸法・枚数・文字サイズと位置・番号・フッター・キャプション・音楽）が全要素一致で記録されている。自社勝者が第一のコピー元である面（EN @aniccaaffirmation／JP @anicca.jp）では、自社勝者のスペックが照合先である。(c) 全スライドに目視判定と pixelmatch 相違率が記録され、合格実測（英語面 8.7〜12.3%／日本語面 1.8〜3.0%／Honne 2.7〜4.8%）を大きく超えるスライドは出さない。端切れ・言語混在は、相違率が合格でも不合格。(d) 全投稿に台帳（posts-ledger）の出典ペア「自社投稿 ← 勝者投稿（実測数字）」がある。
2. **Grader**: 作った本人でない側が、自社版と勝者を並べて全スライドを目視で採点する。pixelmatch は文字切れを検出できないため、数字だけの合格は存在しない。
3. **E2E 証拠**: 予約登録後に posts:list を再読し、件数・枠時刻・重複なし・error null を実測する。公開後は自社投稿の数字を tikwm で実測し、勝者の数字と並べて台帳に残す。
4. **Oracle**: ダウンロードした勝者の実物そのものが照合先である。「〜風の形式」という記憶や型名は oracle にならない。勝者の実物が開けない場合は制作を止め、実測し直すか勝者を固定し直す。
5. **再発防止**: 同じ欠陥（端切れ・太字化・言語混在）が2回出たら、注意喚起ではなくビルダー側のゲート（自動チェック）にして同日中に組み込む。
