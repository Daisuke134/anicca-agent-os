# CLI委任の完了通知ルール

Claude Code／Codex／Devin 等の CLI ワーカーへ仕事を委任したら、起動と同時に「完了が届く仕掛け」を必ず付ける。今回限りではなく、全ての委任に適用する常時ルール。

## なぜ要るか

切り離して走らせただけのプロセスは、終わっても委任した側に「完了」が自動で届かない。委任した側が自分で確認しに行くまで分からず、聞かれて初めてチェックする形になる。これは段取りミスであり、仕組みで防ぐ。

## 仕掛けの選び方（起動時に決める）

1. **第一選択: 切り離さずフォアグラウンドで走らせ、結果が自動で届く形にする。** ランタイムが完了を届ける経路（サブエージェント、完了ハンドオフのあるバックグラウンド実行）を使う。委任した側がポーリングしに行く形にしない。
2. **長時間の作業は、完了マーカーを見張るウォッチドッグを併用する。** 完了マーカーとは「プロセス終了＋成果物（ファイル／コミット）の着地」。実例: Codex 委任は codex-outbox-wake-vm が状態ファイルと着地（ブランチの新規コミット）を見張り、ack を返す形が正。
3. **仕掛けを付けられない場合は、起動時点でその旨を伝える。** 「この実行には完了通知が付いていない。◯時にこちらから確認する」と起動報告に明記する。沈黙を後から発見させる形は禁止。

## 完了通知の中身

- 通知は証拠つきでなければならない: 成果物のパス／コミット／URL を含める。「終わりました」だけの通知は完了として数えない。
- 着地の検証（活動の新しさ＋成果物の実物確認）は delegated_execution_verification スキルの担当。本スキルは「戻り経路が存在すること」自体を保証する。
- 失敗・中断も通知の対象である。終わらなかったことが届かないのが最悪の形。

## 状態確認はマーカーだけを見る（2026-11-17、X 実読から追加）

- ウォッチドッグや委任側の状態確認は、完了マーカー（プロセス終了・新規コミット・成果物ファイルの有無）だけを見る。実行中ワーカーのログ全文や会話を毎回読み直して状態を把握する形は禁止（並列数が増えるほどコストが膨らんで破綻する）。根拠: Anthropic 公式は background subagent の状態行を「短いメモから生成する」形に変え、状態更新あたりのコストを約99%削減した（@ClaudeDevs、https://x.com/ClaudeDevs/status/2118063143167693011）。
- 並列の既定形: 同時に走らせる委任は worktree を分け、worktree／ブランチにタスク名をつける。誰が何をしているかが一目で分かる状態が、完了通知が機能する前提である。

## 禁止形

- nohup＋& で切り離して、見張りを付けずに放置すること。
- 委任先の受領（ack）だけを「動いている」根拠にすること。
- 完了したかどうかを、聞かれるまで確認しないこと。
