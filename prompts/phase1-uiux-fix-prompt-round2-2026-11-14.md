# 委任 第2ラウンド: 質問の拡張と適応化（Anicca iOS、Issue #9353）

これは ROUTE: LOCAL 相当のコード作業である。対象はこの作業ディレクトリ（Daisuke134/anicca のブランチ `claude/phase1-personalized-onboarding`、PR #9352）の `apps/mobile/anicca-ios`。第1ラウンドの修正（F-01〜F-13、commit `1f26b0f42`）の上に続ける。GitHub Issue #9353 に紐づく作業である。

## 仕様変更の要点（2026-11-14 18:30 JST、本人確定）

1. **質問は減らすな、増やせ。** 現行の質問は少なすぎて、個人化にも合成ユーザー（synthetic user）にも足りない。合成ユーザーを作って行動シミュレーションを始めるには、もっとデータが要る。「研究の問いとデータが一番大事」。勝者 I am は25ステップ（ScreensDesign 実測、約2分33秒: 名前 00:27、星座 00:39、バンドルの案内 01:39、ペイウォール 02:33）。流れ全体の規模はこの実測に寄せる。
2. **各質問はユーザーモデルのデータとして設計する。** 各質問について「この答えが合成ユーザーのどのデータになるか」を仕様に明記し、その対応表をコード側の記録（FIX-NOTES 第2ラウンド節）に残す。
3. **質問は適応する。** 次の質問は前の答えで変わる（既存仕様: anicca-ops `files/onboarding-answer-change-mapping-2026-11-14.md` 末尾「Adaptive question sequencing — next iteration requirement」と整合させる）。
4. 根拠は自社の研究ファイル: `files/user-simulation-loop-spec-2026-11-14.md`（条件づけの材料はオンボーディング回答と反応履歴。合成ペルソナは algorithmic fidelity のゲートを通す）、`files/behavior-simulation-products-map-2026-11-13.md`、`files/humansand-competitor-research-2026-11-13.md`（Persimmon はプロフィールと履歴で条件づけたユーザーモデルであり、豊富な利用者データが前提）。
5. 進め方は Anthropic の形: エージェントがコードを書き、別のエージェントがレビューし、エージェントがマージする。人間の手順を入れない。あなた（Codex）が実装し、独立レビューは委任元が別のエージェントで回す。
6. App Store Connect への提出は絶対にしない。第1ラウンドの絶対条件（FIX-NOTES への記録、コンパイルが通る状態を保つ、既存テストを壊さない）は引き続き有効。

## 拡張する質問の仕様

既存の質問（welcome、goal=望む状態、name、pain points、struggle frequency、preview、reminder schedule、notification permission、paywall）は残す。その上に次を追加する。各行: 質問 / 選択肢の形 / 合成ユーザーのどのデータになるか / 製品側で何が変わるか。

### 全員に聞く質問（コア）

| # | 質問 | 形 | 合成ユーザーのデータ | 製品で変わること |
|---|---|---|---|---|
| Q-A | 生年月日または星座 | 任意・スキップ可。日付入力または星座の選択 | ペルソナ属性（年齢層・星座）。合成ペルソナ生成の属性軸の1つ（Persimmon のプロフィール項目に相当） | 季節と節目の文脈づけに使う。当たらなかった個人化には使わない |
| Q-B | 今日の気分の土台 | 5段階（とても重い〜とても軽い） | 状態の初期値。Manager の状態遷移モデルとシミュレーションの開始状態 | 最初の介入の強度とトーンを決める |
| Q-C | 信じたい言葉・ありたい姿 | 複数選択（自分を信じたい／静けさ／前に進む力／許し／感謝 等、goal と重ならない軸） | 信念のテーマ分布。合成ユーザーの「望む信念」の条件づけ | アファメーション候補のテーマ加点（desired_state と合成規則で併用） |
| Q-D | 言葉のトーンの好み | 単一選択（やさしい／まっすぐ／詩的／実用的） | 表現の好み軸。同じ刺激への反応差を合成で再現する条件 | 文のスタイル選択（候補の文体タグで選ぶ） |
| Q-E | いまの生活の文脈 | 複数選択（仕事の負荷／子育て・介護／学業／転機／特になし 等） | ペルソナの生活文脈属性。セグメント生成の軸 | 文脈に合わない候補を除外（例: 仕事文脈のない人に仕事の言葉を出さない） |
| Q-F | 一日の錨（ルーティン） | 複数選択（起床直後／通勤／昼休み／就寝前 等） | 受容性の時間窓。シミュレーションで「いつ届くと開くか」の条件 | 通知時刻の初期提案（本人の時刻選択が常に優先） |
| Q-G | これまで試したこと | 複数選択（瞑想アプリ／日記／相談・セラピー／本・動画／初めて） | 介入の履歴。合成ユーザーの「効かなかった手段」の再現条件 | 試して合わなかった手段の言い回しを避ける |
| Q-H | いま始める理由 | 単一選択（限界を感じた／変わりたい節目／誰かの勧め／なんとなく 等） | 動機と緊急度。シミュレーションの継続率の条件づけ | 最初の介入の文の温度（緊急度に合わせる。恐怖を煽らない） |
| Q-I | 静かな時間（邪魔されたくない時間帯） | 時間帯の複数選択または「なし」 | 制約データ。合成ユーザーの不応答の再現条件 | その時間帯は通知を置かない（本人の時刻選択と合成し、衝突したら静かな時間を優先） |

### 適応で出す質問（困りごとの選択で分岐する深掘りモジュール）

困りごと（pain points）の各項目に深掘りモジュールを1つずつ対応させる。選択された困りごとのモジュールだけを、困りごとの直後に挿入する。複数選択された場合は最大2モジュールまで（勝者の所要時間 約2分33秒の規模を守る）。優先順位は選択順ではなく、困りごとの提示順（stress、anxiety、self-doubt、procrastination、sleep）で固定し、テストで固定する。

| モジュール | 質問 | 合成ユーザーのデータ | 製品で変わること |
|---|---|---|---|
| M-stress | 一番重くなる場面（仕事中／人と会った後／朝起きたとき／夜 等） | トリガーの文脈分布 | grounding・stress_relief 候補の時間帯適合 |
| M-anxiety | 不安が強まる対象（先の予定／人の評価／健康／お金 等） | 不安の対象軸 | 対象に合う候補の加点、合わない候補の除外 |
| M-self-doubt | 自分を責める場面（仕事の失敗／人間関係／見た目／子育て 等） | 内なる批判のテーマ | self_trust 候補のテーマ加点 |
| M-procrastination | 先延ばししていること（仕事の課題／連絡／家事／自分の計画 等） | 回避のパターン | small_action 候補の具体化（2分の一歩の対象） |
| M-sleep | 眠れない理由（考えが止まらない／体の疲れとずれ／画面・習慣 等）と、平日の就寝・起床の目安 | 睡眠の文脈と生活リズム（クロノタイプの近似） | 夜の枠の提案と rest 候補の選択 |

### 適応の規則（コードとテストで固定すること）

1. 深掘りモジュールは、困りごとの答えでのみ決まる。固定の一覧を全員に同じ順で出す形にしない。
2. 気分の土台（Q-B）が「重い」側のとき、preview と最初の介入は強度 gentle に固定する（struggle frequency の強度規則と合成し、強い方ではなく穏やかな方を取る）。
3. 錨（Q-F）と静かな時間（Q-I）と本人の通知時刻選択の合成: 本人の明示選択が最優先、静かな時間との衝突は静かな時間を優先し、錨は未選択時の提案にだけ使う（既存の合成規則1「本人の明示選択を優先」と矛盾させない）。
4. 適応で出し分けた質問も含め、全ての答えは安定 ID で UserProfile に保存し、判断点の記録へ snapshot する（既存の計測契約どおり）。分析へ送るのは列挙 ID と version のみ。名前・生年月日の実値・自由文は分析へ送らない（既存の合成規則4を維持）。生年月日は端末内の profile にのみ保存し、分析には年齢層の列挙 ID だけを送る。
5. スキップ可能な質問（Q-A 等）でスキップされた場合、その軸は「不明」として保存し、合成ユーザー生成では欠損として扱える形にする（推測で埋めない）。
6. 再開（resume）互換: 第1ラウンドで追加した name=9 に続き、新しいステップの rawValue は既存値と衝突しない連番にする。旧バージョンの保存値の移行を壊さない。

## 実装上の注記

- 質問画面は第1ラウンドで統一したデザイン言語（系統A）で作る。1画面1問（F-06 のまま）。
- 文言は全6言語の Localizable.strings に追加する。既存の翻訳欠落（第1ラウンドで記録した既存不備）は今回も対象外だが、新規キーの欠落は作らない。
- Maestro フローは、適応分岐を通る経路（困りごとで sleep と anxiety を選び、両モジュールが出ること）を含めて更新し、新しい質問画面のフレームも撮影する。フレームの対応表（ファイル名→画面→監査の番号との対応）を FIX-NOTES に書く。既存の 00〜16 の番号は同じ画面に維持し、新規画面は流れ順の枝番（例: 02b-、03b-）で割り当てる。
- 単体テスト: 適応分岐の規則（モジュール選択・上限2・優先順位）、合成規則（気分の土台と強度の合成、静かな時間の優先）、保存と移行（rawValue の互換）をテストで固定する。
